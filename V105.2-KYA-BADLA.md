# v105.2 RAM-SAVER — Render free 512MB par OOM risk kam (10 Oct 2026)

## Screenshot se kya pata chala
Render email me service `512MB` memory limit paar karke auto-restart hui; Events me
`Service recovered` 6:11 AM par dikh raha tha. Iska matlab instance wapas healthy ho
chuka tha, lekin media kaam/startup ke peaks free limit ke paas ja rahe the. Screenshot
se exact ek tool/trigger identify nahi hota — isliye is release me startup, concurrency,
media-buffer aur watchdog sab par free-tier safety lagayi.

## Kya badla
1. **Heavy imports lazy** (`bot.py`, `modules/media_downloader.py`)
   - `yt-dlp` module import ab pehli real download tak nahi hota (~39MB isolated
     import test me); startup self-check `find_spec()` se sirf installed/missing
     batata hai, library load nahi karta.
   - MTProto/Telethon pre-login default OFF. Badi file aane par existing
     `bigfile.mt_send()` pehli baar client lazily start karega. Pre-login chahiye
     ho to `BIGFILE_WARM=on` explicit option ab bhi hai.
2. **Concurrency** (`modules/core/heavy.py`, `modules/media_downloader.py`)
   - 512MB plan par heavy media jobs ka cap **1**; purana Render env
     `HEAVY_MAX_SLOTS=2` ho tab bhi code hard-cap karta hai.
   - Instagram/media engine race max **2** engines ek saath chalata hai, ek link
     par 8 competing download threads nahi. Winner ke baad queued loser cancel;
     fallback engines/quality choices same hain.
3. **Transfer size + allocation** (`modules/media_downloader.py`)
   - 512MB plan par media buffer cap **48MB** (explicit `MAX_TG_MB=96` ho tab
     bhi safe clamp); bigger-memory service par override possible.
   - Instagram ke parth-dl, embed, Wayback, jina, album/profile-photo aur OG
     fallback media requests size cap ke saath stream hote hain; pehle direct
     `.content` unbounded tha.
   - Fast-path order: parth-dl/embed pehle; yt-dlp sabse aakhir me. Public
     carousel/reel par parth success ho to yt-dlp import/background fetch chalta hi nahi.
   - 40MP se bade compressed photos decode se pehle reject hote hain; normal
     high-res Instagram photos resize-before-RGB conversion se process hoti hain.
   - Chunk buffers `bytearray` in-place grow karte hain; repeated immutable
     `data += chunk` allocation churn band.
4. **Watchdog** (`modules/core/guard.py`)
   - RAM check 60s se 15s; soft clean 76%, aggressive clean 82%; configured
     `MEM_RESTART_MB=470` free-tier limit se pehle ~430MB par clamp hota hai.
   - Restart ab bhi sirf high RAM cleanup ke baad aur bot idle hone par hi hota
     hai; active user ka kaam beech me nahi maarta.
5. `render.yaml` free defaults: heavy slots 1, media cap 48, warm-up off,
   restart threshold 429MB. BOT_VERSION `v105.2 RAM-SAVER`; v105.1 channel
   replace and v105.0 features retained.

## Important trade-off (honest)
Free Render me memory bachane ke liye Telegram par bheje jaane wale media files
48MB tak capped hain. Isse bade YouTube files available hon to direct-link fallback
use ho sakta hai; kuch Instagram large files fail ho sakte hain. HD/quality labels
ab bhi source file ki measured quality par hi hain. Ye configuration free instance
ko zyada stable banane ke liye hai — Render ke hard 512MB limit ko code se badla nahi
ja sakta, isliye kisi bhi unpredictable third-party library/process ke liye absolute
zero-OOM guarantee dena sahi nahi hoga.
